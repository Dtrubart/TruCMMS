# Completion, acceptance and closure — step 6

Work orders now separate Technical Completed, Accepted and Closed. The assigned enabled/scoped technician declares completion with a summary after recording completed tasks for the current execution cycle/assignment. The original requester accepts service or requests rework with a reason. An independent supervisor can Accept on Behalf with justification; the completing technician cannot accept their own completion, even with multiple roles. A supervisor closes only accepted work. All actions require a reason/summary.

Rework returns work to Assigned and advances execution_cycle. New execution must occur after the rework decision; the previous cycle cannot be used to complete again or receive further evidence. Prior execution and decisions remain available. Latest completion/acceptance/closure fields are snapshots; immutable TruCMMS Work Event records and native Version preserve the sequence of attempts and decisions.

Cancellation is allowed to a supervisor in Draft, Authorized, Assigned or Technical Completed. Accepted or Closed work cannot be cancelled. Cancelled/Closed orders are terminal and immutable, preserving requests, assignments, execution and evidence. The single corrective order per request remains linked even when cancelled; this release does not recreate/reopen cancelled orders automatically.

The request keeps Approved as its authorization decision. Operational fulfillment is the linked order's status; the original requester gains scoped access after technical completion or cancellation and can use View Work Order from the request. Requesters can inspect authorized execution/evidence for acceptance. Technicians retain scoped read of their assigned order history after completion; recording/uploading is allowed only in Assigned, for the correct cycle. Evidence freezes at technical completion and terminal states.

Lifecycle actions use a POST-only endpoint that checks role, Company/Site, current state and required reason; locks the order; validates the transition; saves the order and immutable event in one request transaction. Direct status/audit field mutations and unreasoned native workflow API actions are rejected. Native Desk action buttons and workflow menu actions open a summary prompt and call the controlled endpoint. Order conversion is also POST-only.

The managed three-state workflow is upgraded to seven states. Matching original state/transition contracts are upgraded; differing original contracts require explicit review rather than silent overwrite. Existing orders retain their identities/assignments and receive original-requester/cycle backfills; execution rows receive cycle 1. The upgrade is idempotent. No application-specific SQL ledger or ERPNext core edit is introduced.

Local checks: 16 lifecycle cases plus 97 previous tests. Native Desk/HTTP verification covered technical completion, reasoned rejection/rework, new execution, requester acceptance, supervisor closure, immutable events, cross-company denial and cancellation with requester tracking. Corrections/voiding of erroneous execution entries, general workflow configuration, notifications, production recovery and reporting remain subsequent work; do not silently change historical durations.
